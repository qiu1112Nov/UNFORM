# UNFORM 3.2.1 性能测量

基线：main `bdc2cd4`（3.2）。本次先测量后优化；没有把猜测当作安卓真机瓶颈结论。

## 环境与方法

同一云机器的 Headless Chromium，390×844 CSS 像素，设备 DPR 请求 3（应用限制为 1.5），CDP 主线程 CPU 4 倍限速。预热 30 帧，采样 240 次手动 `update + draw`，分别测试静止、完整编织和快速模拟手移/轨迹。使用真实 Canvas 与 CPU Profiler；摄像头在这组测试中关闭。前后测量串行执行，没有让两个 benchmark 同时争用 CPU。

`update` 包含 `projectAll`，`draw` 包含 `drawWeave/drawTraces`，这些子项不能重复相加。这里测的是同步 JS/Canvas 提交，不是显示合成或真机 FPS。基线少量 Canvas 队列刷新长帧显著抬高均值，所以同时报告 P95，不将均值换算成承诺帧率。

| 场景 | 3.2 平均 / P95（ms） | 3.2.1 平均 / P95（ms） | stroke 次数/帧（前→后） |
| --- | --- | --- | --- |
| 静止 | 5.41 / 7.90 | 2.13 / 3.80 | 72 → 1 |
| 完整编织 | 21.35 / 7.40 | 2.34 / 3.50 | 432 → 2 |
| 快速手移与轨迹 | 16.42 / 8.40 | 2.19 / 3.40 | 约 439 → 约 4 |

基线 CPU 采样中 `stroke` 自耗时最高。完整编织的同步绘制均值约 20.22ms，而粒子更新约 1.11ms。因此先合批手机线条，避免仅减粒子却保留数百次逐线提交。新默认 595 个可见粒子，预算池仍为 850；默认 TRACE 4 个采样，原为 7 个。不同运行与设备会有变化，上表是一次受控前后记录，不是保证收益。

## 摄像头推理测量与处理

使用真正的 MediaPipe 0.10.32 CPU 模型和 Chromium 伪视频（画面无真实手）。官方模型通过正常 TLS 校验的 curl 下载，并核对官方 HTTPS ETag/MD5 `15318430ea3851670fe9914116a9cfad`；因云浏览器自身对上游证书报错，测试将该已验证文件注入模型请求，没有关闭 TLS 检查。实际应用仍从官方 URL 下载模型。

基线主线程模型推理均值约 143ms，摄像头开启后独立 RAF 采样约 45.2fps。3.2.1 使用 Worker 后，同一主线程限速设置下 RAF 采样约 59.7fps，595 个目标粒子，单 Worker 推理均值约 31ms。**主线程 CPU 限速不会等比例作用于 Worker，不能据此声称模型算法加速了 4 倍**；这组结果只支持“将重推理移出主线程能避免其直接冻结动画”的架构判断。伪视频无手时的检测开销也不等于真实手部持续追踪开销。

Worker 不排队历史帧，仍使用原新帧去重、最高约 30Hz 与推理成本自适应策略。Worker 不可用或初始化失败时回退原路径；回退模式下重推理仍可能卡住主线程，调试面板会明确显示执行模式。没有通过加大确认窗口或固定等待换取帧率。

## 自适应与桌面质量

- 初始手机预算 595，档位为 425/510/595/722/850；外部结构比例和 FLOW 比例按档位精确取整。
- 观察真实帧间隔和主线程更新/绘制耗时。持续压力约 2 秒才降档，健康约 8 秒才升档，冷却 4 秒，粒子在约 450ms 内过渡。后台大间隔、暂停和恢复计时不用于连续降档。
- 预分配池、选择掩码和 TypedArray 轨迹缓存不在每帧重建。流动路径复用数据，固定相位的三角函数预计算，恢复指数移至逐帧一次计算。
- 桌面保持 1900 粒子、DPR 上限 2、12 个 TRACE 采样和原逐线样式，不参与手机质量降档。
- `?debug=performance` 中更新/绘制数字为主线程提交耗时，FPS 为帧间隔 EMA；不要把 Worker 推理耗时与主线程耗时简单相加。
